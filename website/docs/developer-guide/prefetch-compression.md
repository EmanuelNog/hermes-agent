# Prefetch Compression (non-blocking automatic compaction)

Status: proposal / patch under review. Public fork + branch:
[github.com/EmanuelNog/hermes-agent](https://github.com/EmanuelNog/hermes-agent)
(branch `prefetch-compression`); this document is the review copy.

Source files: `agent/turn_prefetch_compaction.py` (new), `agent/turn_preflight.py`,
`agent/turn_context_compaction.py`, `agent/turn_overflow.py`, `agent/turn_recovery.py`,
`agent/agent_init.py`, `hermes_cli/config_defaults.py`, `agent/conversation_compression.py`,
`gateway/run.py`, `tests/agent/test_prefetch_compaction.py`,
`tests/agent/test_prefetch_upstream_compat.py`.


## TL;DR

Automatic context compaction currently BLOCKS the agent loop while the summary is
generated (minutes on large sessions). Prefetch compression starts the summary
worker slightly EARLIER, in the background, while the loop keeps executing — and
adopts the finished summary at a later safe gate. The existing blocking path is
kept untouched as the backstop. Off by default: `compression.prefetch_margin: 0`
behaves exactly like today.


## Problem

When prompt tokens cross the compression threshold, the only option today is to
halt and summarize synchronously. Measured on a real 519K-token session: 4m13s of
dead time in the gate (253s / 116s / 159s across three sessions; pre-#96603 builds
took 17–24 minutes). The summary is generated by a pool worker thread either way —
blocking is a policy choice, not a structural one.


## Design

### Trigger

New config key `compression.prefetch_margin` — a fraction of the context WINDOW,
subtracted from the blocking threshold:

```
arm at      threshold_tokens − prefetch_margin × context_length
block at    threshold_tokens                                  (unchanged)
```

```
 tokens
   |
   |                                   ●── blocking compaction (unchanged, backstop)
   |                        ┌──────────┘
   |     ○  arm worker      │  adopt at next gate:
   |     │  (non-blocking)  │  summary + live suffix
   | ────┴──────────────────┴──────────────►  time
   |   margin band          threshold
```

With production settings (`threshold: 0.65`, `prefetch_margin: 0.05` on a 1M
window) the worker arms at ~60% fill and runs while the loop continues; nothing
blocks unless the 65% threshold is reached before the worker lands.

### Lifecycle

- **arm** — at any compression gate inside the margin band: freeze a shallow
  snapshot of the live message list, submit the same summary worker the blocking
  path uses (`compress_context`) on the shared compression pool, publish its
  commit fence for `/stop`.
- **adopt** — at a later gate: splice `worker_result + live_suffix` (everything the
  conversation gained after arming stays verbatim), then run the normal
  post-compression plumbing (history re-baseline, retry-state reset).
- **discard** — if the live prefix no longer equals the frozen snapshot (rewind,
  edit-resend, or another compaction happened), the result is stale and dropped.
  Discards are silent, like today's no-op passes.
- **threshold hit while pending** — adopt if done; else bounded wait (≤60s) for
  the in-flight worker; else degrade into the existing timeout path (the worker
  owns the session compression lease, so the blocking pass lock-skips safely).

### Invariants

- **`prefetch_margin: 0` is byte-identical to current behavior.** All new code is
  inert when the margin is 0.
- **Scope: automatic in-loop compaction only.** Manual `/compress`, gateway
  session hygiene, Codex app-server, and Responses-native compaction are
  untouched — the last two are explicitly refused by the arming ballot
  (provider-owned compaction must not be double-compacted).
- **Arming requires a fully persisted region** (every live row carries the
  persisted marker) so the worker's DB commit can never overlap a main-thread
  flush of the same rows — the invariant that prevents duplicate rows.
- **Staleness is acceptable by design**: the summary covers up to the arming
  point; the newest margin-worth of conversation survives verbatim in the tail.
- **The seam never splits a tool pair**: the splice point is exactly where the
  live list was cut at arming.


## Implementation

One new module (~400 lines, `agent/turn_prefetch_compaction.py`):

- `prefetch_trigger_tokens` — trigger math, clamped `[0, threshold−1]`.
- `can_prefetch` — ballot: disabled / codex app-server / responses-native /
  rotation mode / margin 0 / already pending / no compressor / outside band /
  failure cooldown / attempts exhausted / unpersisted rows / pool admission.
- `launch_prefetch_compression` — snapshot freeze, pool submit, fence publish,
  state registration on the agent.
- `run_prefetch_compaction_step` — the single entry point the gates call; returns
  `none | armed | pending | adopted`; owns adoption, discards, the bounded await,
  and failure handling.
- `adopt_prefetch_result` — prefix-identity staleness check + splice + a
  seam-dedupe safety net.
- Reporting helpers (see below).

Wire-up is five call sites in four gate files — each is the same 8-line block:
`turn_preflight.py` (pre-API + post-tool gates), `turn_context_compaction.py`
(turn start), `turn_overflow.py` (413 recovery), `turn_recovery.py` (Anthropic
long-context). While a worker is pending/armed, those sites skip the blocking
compression branch — mirroring the existing lock-skip semantics.

Config plumbing: `hermes_cli/config_defaults.py` (`prefetch_margin: 0.0`) +
`agent/agent_init.py` (parse + `agent.compression_prefetch_margin`).

**Reporting** (native style, same registers as blocking compaction): start
`🗜️ Compacting context (prefetch) — …` via `_emit_status` (TUI tags it
"compacting"); done `✓ Prefetch compaction complete — N → M messages in Xs` via
`_emit_status_kind("compacted", …)` with the true worker duration (stamped by a
done-callback, not the adoption delay); failure `⚠ Prefetch compaction failed
after Xs (reason)` via `_emit_warning`. Templates live in
`agent/conversation_compression.py`; the gateway classifies them exactly like the
blocking statuses (suppressed on chat surfaces by default, deliverable with
`compression.progress_notices`, failure always visible).

### Safety notes (from the implementation audit)

- `/stop` cancels the worker before its commit via the published fence.
- A worker that fails mid-flight clears its state and lets the blocking backstop
  proceed; failures ride the existing cooldown ladder.
- Process death between arm and adoption self-heals: the worker's DB commit is
  durable and independent of adoption (resume sees a compacted session).
- A pending state from a previous session is dropped at the gate.
- The blocking backstop re-checks after adoption (post-adoption estimates can
  still cross the threshold → the normal blocking pass fires — verified live).
- Rotation mode (`compression.in_place: false`) is refused: the worker rotates
  session ids at commit, which cannot be spliced safely mid-turn.


## Evidence

### Tests (0 failures)

- `tests/agent/test_prefetch_compaction.py` — 54 behavior tests: trigger math,
  every ballot refusal, launch/admission/fence, in-process arm→adopt, all
  adopt/discard branches, threshold policy, reporting, duration math.
  Module coverage: **100%**.
- `tests/agent/test_prefetch_upstream_compat.py` — 13 host-integration pins
  (compress_context kwargs, fence API, admission pair, persisted marker, gate
  names, config parse). These fail loudly (named seam) on host refactors.
- Regression on the merged tree: 922 tests across the compression/compaction
  family + gateway noise filter; 133 turn-loop tests.

### Live validation (real sessions, real providers)

- Small scale (64K window, threshold 40K, margin 0.15): armed ~34.8K → adopted
  43s later (176→100 messages, live suffix preserved), re-armed, adopted again;
  76 tool calls in 2m05s with zero blocking.
- 1M window, threshold 0.75, margin 0.05 (~60% fill): armed at ~728,809 real
  tokens 0.24s after the response; **four full-size API calls across two turns
  ran while the 6m12s worker was active**; adoption 758→103 messages; the next
  request went out at 85,146 tokens (**−88%**); zero blocking lines.
- Chat reports verified live: `🗜️ … (prefetch) …` on arm and
  `✓ Prefetch compaction complete — 176 → 96 messages in 20s, continuing…`.


## Config reference

| key | default | meaning |
|---|---|---|
| `compression.prefetch_margin` | `0.0` | fraction of the context window; arms a background summary at `threshold − margin × window`. 0 = disabled. Recommend `0.05`. |

```yaml
compression:
  threshold: 0.65
  prefetch_margin: 0.05   # arm ~60% of window; block at 65% (unchanged)
```


## Review guide

1. Read `agent/turn_prefetch_compaction.py` top-to-bottom — it is self-contained.
2. Diff the five gate call sites (small, uniform blocks).
3. Check the invariants above against the ballot and the adoption path.
4. `scripts/run_tests.sh tests/agent/test_prefetch_compaction.py tests/agent/test_prefetch_upstream_compat.py`
5. Try it live: profile with `compression.prefetch_margin: 0.05`, drive any
   session past ~60% fill in a persistent process, watch for the report lines.
   (Adoption requires a persistent process — one-shot `chat -q` exits before the
   worker lands.)


## Limitations / follow-ups

- **Cost trade-off (by design):** a session that crosses the arming point but
  ends below the blocking threshold still pays the background summary. The margin
  is the spend/latency knob.
- `micro_compact` + prefetch is unsupported (both rewrite sent history); do not
  enable both.
- Lean-tail floor (10K tokens) makes tiny sessions uncompressible — dev testing
  used `tail_mode: legacy`; production keeps lean.
- Follow-up candidates: per-model margin presets; heartbeats reusing the worker
  fence; an upstream-engine hook so plugins can observe prefetch events.
